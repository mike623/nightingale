# Phone remote control rides a dumb relay, never a second API

The Remote lets a phone on the local network drive the running Song. Audio stays where it already is — the host page, desktop webview or browser — so the phone needs a two-way channel to that page, not access to the library. The relay is exactly that and nothing more: it fans frames between the host page and connected phones, remembers the last snapshot so a phone that joins mid-song renders immediately, and arbitrates which phone holds control. It never calls `app_core`. The phone's capabilities are whatever the host page chooses to answer, which is why a later feature like picking the next Song from the phone needs no new server surface at all.

One implementation serves both delivery targets. The relay lives in its own crate; the self-hosted server merges it into its existing `/ws` route, and the desktop build starts it as a small listener of its own because Tauri has no HTTP surface — `app-core`'s media server binds loopback only and speaks no WebSocket, so it could not carry this. The desktop listener is opt-in (`remote_control`, default off) and started from the UI, so no install begins listening on the network unasked, and it exposes only the WebSocket and the embedded page. Rejected: lifting the whole self-hosted API into the desktop app, which would publish `clear_all` and stored Source credentials to the network; and an SSE/POST channel over the existing media server, which would have forked either the protocol or the mobile UI away from the self-hosted build.

There is no authentication, matching this server's existing posture — `/api/cmd/:name` is already unauthenticated on the same network. The consequence is explicit and must stay documented for operators: anyone who can reach the port can open the Remote and control playback. The bounded route surface is what keeps that acceptable, so widening the relay beyond the socket and the page would break the reasoning this decision rests on. Inbound frames are still treated as untrusted input — size-bounded, shape-validated, and clamped — because a relayed frame is written by another client, not by the host.
